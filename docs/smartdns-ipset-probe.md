# Контрольная проверка SmartDNS → ipset

На Hopper установлен SmartDNS 46.1, основной DNS :53, `opkg dns-override`.
Штатный FQDN domain-list9 с api.ipify.org не получает динамические адреса,
но два явных CIDR в этой группе успешно направляют LAN через FPTN.
Набор `_NDM_OGDN_4_@domain-list9`: hash:net revision 2, без timeout.

Первая проверка была неоднозначной: после удаления CIDR через ndmc оба адреса
остались в наборе ядра ещё ДО запроса DNS. Поэтому неизменившееся содержимое
не подтверждало и не опровергало запись SmartDNS. Та версия теста заменена.

Текущий `probe-smartdns-ipset.sh` создаёт отдельный **неиспользуемый правилами**
набор `fptn_probe_4_@PID` типа hash:net без timeout. Набор обязан отсутствовать
до создания и быть пустым после создания. Чужие/рабочие наборы, конфигурация
NDMS и маршрутизация вообще не изменяются.

На время до 15 секунд запускается второй foreground SmartDNS на
127.0.0.1:15353 с cache-size 0 и единственным upstream 127.0.0.1:53.
В отдельной временной конфигурации одно правило ipset для api.ipify.org.
Кеш/журнал/pid находятся в mktemp-каталоге.

Выполняется nslookup через 127.0.0.1:15353. Печатаются Members до/после.
PASS возможен, только если IP из полученного DNS-ответа появился в новом наборе.
Пустой, не относящийся к ответу либо уже заполненный до запроса набор успехом
не считается. Это проверка записи SmartDNS в hash:net, а не доказательство
готовности постоянной интеграции с внутренним набором Keenetic revision 2.

При завершении/обычном прерывании/ошибке процесса временный SmartDNS
останавливается, только собственный набор уничтожается, файлы удаляются.
При ошибке удаления набора выводятся его точное имя и ошибка.
SIGKILL и отключение питания trap обработать не может.
Основной SmartDNS, порт 53, его серверы и статистика клиентов остаются прежними.

Это не постоянная схема доменной маршрутизации. Прямые записи в ipset не наполняют
внутреннюю DNS-модель ndm; счётчик динамических FQDN-адресов в GUI может остаться
нулевым. Наборы Keenetic не поддерживают timeout: окончательное решение потребует
управления устаревшими адресами/пересозданием наборов и синхронизации списков.
Имена наборов являются деталями реализации Keenetic.

Локальные тесты используют моки: положительная запись ответа, ответ без записи,
ошибка запроса/запуска, коллизия имени, непустой начальный набор, очистка
временного набора и файлов, отсутствие обращений к ndmc и рабочим наборам.
Реальная netlink-запись проверяется только запуском сценария на роутере.

Синтаксис подтверждён в [SmartDNS Release46.1](https://github.com/pymumu/smartdns/blob/Release46.1/etc/smartdns/smartdns.conf).
