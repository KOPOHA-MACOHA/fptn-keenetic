# Проверка расхода памяти очереди пакетов

Клиент 0.8.1 исправляет превышение заданного лимита `Channel::PushBatch`.
Раньше проверялось только текущее заполнение очереди: при 4095 пакетах и лимите
4096 целый блок из 16384 пакетов принимался, увеличивая очередь до 20479.
Такой размер блока возможен при выгрузке накопившейся очереди VPN-менеджера
в очередь отправки TUN.

Теперь блок принимается целиком, только если помещается в оставшееся место.
Иначе метод возвращает `false` и освобождает непринятые пакеты. Это сохраняет
смысл результата для вызывающего кода и не допускает частичной доставки блока.
При перегрузке возможно большее число отброшенных пакетов по сравнению с
прежним превышением лимита. Лимиты очередей, протокол и настройки маршрутов
не изменяются. В обычном режиме все пакеты продолжают передаваться.

## Воспроизводимый стенд

Используются реальные `Channel` и `IPPacket`. Исходный заголовок сохранён
в `tests/fixtures/channel/channel.h`, текущий берётся из `src/`.
Бенчмарк, тесты и результаты находятся только в исходниках, не в устанавливаемой
службе. Во время теста нет VPN-подключений, TUN, запросов к серверам или
изменений сети. Логирование отключено одинаково в обоих вариантах.

Локальный замер: Linux x86_64, glibc 2.41, Boost 1.83.0, spdlog 1.17.0.
Это **замер компонента на стенде**, а не всего клиента и не роутера.
Медианы независимых процессов:

| Сценарий | До | После |
| --- | ---: | ---: |
| Обычная передача, принятые / прочитанные пакеты | 640000 / 640000 | 640000 / 640000 |
| CPU обычной передачи, секунд, 5 запусков | 0.075764 | 0.075023 |
| Перегрузка: пакетов, оставшихся в очереди | 20479 | 4095 |
| Перегрузка: RSS после нагрузки, КиБ, 3 запуска | 31280 | 7864 |
| Перегрузка: пиковый RSS, КиБ (`VmHWM`), 3 запуска | 54460 | 30984 |

Разница RSS под перегрузкой — около 23 МиБ. Она не переносится автоматически
на другие libc, архитектуры или весь клиент. Разница CPU обычной передачи
мала относительно разброса запусков; ускорение не заявляется.
Расход памяти в простое заметно не изменился.

Обычный сценарий: 20000 блоков по 32 пакета размером 1400 байт с немедленным
чтением. Перегрузка: очередь ёмкостью 4096, начальное заполнение 4095,
12 входящих блоков по 16384 пакета без работающего потребителя.
Это проверка удерживаемой памяти и границы очереди, не замер скорости VPN.
Полные результаты: [JSON](benchmarks/channel-memory-2026-11-12.json).

Тест проверяет FIFO, точное заполнение, атомарный отказ, возобновление после
отказа и четырёх одновременных производителей. CI повторяет сравнительные
замеры, проверяет клиентские бинарники и эмулирует CLI; это не испытание
пропускной способности VPN на реальном оборудовании.

```sh
python3 -m unittest discover -s tests -p test_channel_memory.py -v
```

Нужны `g++`, заголовки Boost и spdlog. Для отдельных каталогов заголовков
поддерживаются `FPTN_BOOST_INCLUDE` и `FPTN_SPDLOG_INCLUDE`.

## Проверенный, но не включённый кандидат

Резерв WebSocket-буфера 4 МиБ сравнивался с 64 КиБ на двух буферах, включая
128 циклов записи сообщения размером 256 КиБ. Зарезервированная ёмкость
уменьшалась, но RSS оставался примерно одинаковым: около 2.2 МиБ для процесса
компонентного теста. Изменение резерва в выпуск не включено.
