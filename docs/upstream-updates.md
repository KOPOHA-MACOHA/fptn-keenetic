# Поддержка обновлений оригинального FPTN

`Check original FPTN releases` проверяет стабильные выпуски fptn-project/fptn
ежедневно около 07:23 UTC (GitHub может задержать расписание), по кнопке Run workflow,
а также после изменения самого проверяющего сценария. Проверки идут в GitHub,
не на роутере. Отдельный персональный токен не нужен.

Проверяющий сценарий выбирает максимальную стабильную версию формата X.Y.Z/vX.Y.Z,
исключает draft/prerelease и разрешает тег в полный SHA. Текущий SHA берётся из
sources.lock.json на актуальном main. Одинаковая или более старая версия не создаёт
PR и не запускает дорогую сборку. Расхождение истории требует ручного разбора.

Для новой версии создаётся отдельная ветка auto/upstream-VERSION-SHA и draft PR.
Меняются только SHA FPTN в sources.lock.json и метаданные sources.upstream.json.
Четыре зависимости остаются закреплёнными: обновить их можно отдельно при
конкретной необходимости. Текущие исходники оригинала по-прежнему не копируются
в форк. Существующие ветки не перезаписываются, force push не используется.
Повторная проверка того же выпуска не создаёт второй PR/сборку, даже если PR
закрыт. Если создание PR прервалось после создания ветки, повторная проверка
продолжит с сохранённой ветки, проверив её lock-файл.

## Проверки кандидата

Поскольку GITHUB_TOKEN не запускает pull_request workflows после собственного
создания PR, проверяющий workflow явно вызывает reusable Build prototype и
Check runtime and panel с SHA коммита кандидата. Все checkout в этих workflow
используют переданный SHA. Выполняются адаптации, тесты, MIPS cross-build,
проверка ELF и QEMU, существующие тесты панели и установщика. Артефакт клиента
доступен в запуске workflow; итоговый check прикрепляется к SHA PR. При ошибке
в summary есть ссылка на PR и запуск с логами. Автоматического исправления
изменившегося протокола, merge или установки на роутер нет.

Публикация native-релиза в reusable сборке отключена. Только обычная успешная
сборка main после merge может опубликовать клиент. Каталог web/update.json для
роутера обновляется отдельно после проверки выпуска, в том числе на устройстве.
Версия клиентского порта и версия оригинального FPTN — разные значения:
клиент 0.4.0 сейчас основан на оригинальном FPTN 0.4.6. При выпуске нового
бинарника нужно обновить версию порта и соответствующие clientVersion/clientRevision
каталога; один успешный PR не меняет установленный клиент.

## Разрешения и повторная проверка

Discover получает contents:write и pull-requests:write для создания обычного
коммита, новой ветки и PR в этом форке. GitHub должен разрешать Actions создавать
PR (Settings → Actions → General → Workflow permissions → Allow GitHub Actions
 to create and approve pull requests). Сценарий не одобряет PR. Если настройка
запрещена организацией/репозиторием, он завершится понятной ошибкой; ветка
останется сохранённой. Административные настройки сценарий не меняет.

Сборочные jobs получают contents:read и не сохраняют git credentials. Вызывающий
workflow допускает contents:write как верхнюю границу разрешений существующего
publisher job; publisher при переданном source-ref безусловно пропускается.
Report получает checks:write только для публикации результата проверки SHA.
Сценарий API запрещает любые записи вне KOPOHA-MACOHA/fptn-keenetic.

При временном сбое используйте Re-run failed jobs исходного запуска: outputs
Discover сохраняются, повторно запускается нужный build. Если требуется изменить
исправления адаптации, внесите обычный коммит в ветку PR — обычные pull_request
проверки запустятся для этого изменения. Закрытый PR намеренно не открывается
автоматически; его можно открыть повторно и запустить проверки вручную.
