# Обновления оригинального FPTN

`Check original FPTN releases` ежедневно проверяет стабильные выпуски
[fptn-project/fptn](https://github.com/fptn-project/fptn), а также запускается
вручную и после изменения проверяющего сценария. Проверки выполняются в GitHub.
Персональный токен и доступ к роутеру не нужны.

## Что попадает в PR

Выбирается максимальная стабильная версия X.Y.Z/vX.Y.Z без draft/prerelease.
Тег разрешается в полный SHA. Одинаковая или более старая версия не создаёт
ветку, PR или сборку. Расхождение истории требует отдельного разбора.

Для нового выпуска готовится настоящий merge исходников в изолированном
worktree. Коммит имеет двух родителей: текущий main и оригинальный выпуск.
Обновляются `sources.lock.json` и `sources.upstream.json`; четыре внешние
зависимости остаются закреплёнными. README и служебные файлы форка сохраняются.
Активные workflows оригинала не включаются: их копии сохраняются в
`.github/upstream-workflows/*.disabled`. Неизвестные конфликты исходников
останавливают подготовку, не меняя main.

Ветка `auto/upstream-VERSION-SHA` и draft PR создаются только после подготовки
целого дерева. Существующая ветка не перезаписывается. Повторная проверка не
создаёт дубликатов, включая закрытые PR. После сбоя создания PR можно продолжить
с сохранённой ветки: проверяются её source lock и наличие оригинального коммита
среди предков. Автоматического merge, смены протокола или установки нет.

## Проверки до слияния

GitHub не запускает PR workflows после создания PR через GITHUB_TOKEN, поэтому
проверяющий workflow явно вызывает `Validate upstream sources` с точным SHA.
Он проверяет runtime, панель, установщик и изолированные сетевые сценарии;
отдельно компилирует клиент для MIPS, ARM64 и ARMv7, проверяет ELF и запускает
офлайн CLI/защитные проверки под QEMU. Клиенты сохраняются как Actions artifacts.
Итоговый check прикрепляется к коммиту PR. Аппаратных испытаний и реального
VPN-подключения эти проверки не заменяют.

Весь workflow совместимости имеет только чтение репозитория. Он не выпускает
релизы, не обновляет каталог панели и не собирает Conan с нуля. Отсутствующий
снимок SDK или несовместимость дают явную ошибку. После исправления ветки PR
его точный SHA можно проверить через Run workflow → Validate upstream sources.

## Сохранение кешей

Если рецепты, CMake-входы и внешние SHA не изменились, updater записывает
`build-locks/source-reuse.json`: точный исходный lock SDK, хеш нового lock клиента
и контракт файлов зависимостей. Ключи SDK остаются прежними для каждой архитектуры;
используются проверенные постоянные OCI-снимки, а не повторная сборка библиотек.
Последовательные обновления сохраняют ссылку на первоначальный SDK.

Перед компиляцией внутри восстановленного образа сравниваются уже подготовленные
рецепты/CMake-файлы, ABI-профиль и полный набор lock-файлов. Затем проверяются
инструменты и полный граф Conan без обращения к remotes. Два ранее проверенных
ARM-снимка, созданных до locks, допускаются только по точным OCI-хешам из
`build-locks/cache-imports.json`; отсутствие locks у другого образа — ошибка. Только после этого
неизменённые locks привязываются к новым исходникам внутри сборки. Исходный
`build-locks/metadata.json` в репозитории продолжает описывать кешированный SDK,
а клиентский артефакт получает актуальный `sources.lock.json`.

Если upstream меняет рецепты или CMake-входы, PR помечается `refresh-required`.
Проверки останавливаются до загрузки SDK; требуется явное обновление
[build locks](build-locks.md) и проверенных снимков. Автоматического выбора новых
версий зависимостей и скрытой долгой пересборки нет.

## Разрешения и публикация

Discover получает `contents:write` и `pull-requests:write` для новой ветки и draft
PR только в этом форке. В GitHub должна быть разрешена настройка Settings →
Actions → General → Workflow permissions → Allow GitHub Actions to create and
approve pull requests. Сценарий не одобряет PR и не меняет административные
настройки. При запрете ветка сохраняется, ошибка указывает на разрешения.
Report получает `checks:write` только для результата проверок.

Временные ошибки проверок можно повторить через Re-run failed jobs. Закрытые PR
не открываются автоматически. После осознанного merge обычный
[конвейер публикации](release-publication.md) проверяет сборки всех архитектур
и runtime перед обновлением пользовательского канала. Один успешный PR ничего
не меняет на уже установленных роутерах.
