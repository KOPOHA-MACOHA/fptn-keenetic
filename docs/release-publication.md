# Автоматическая публикация проверенных выпусков

`Publish verified releases` запускается после завершения `Build prototype`,
`Build experimental ARM ports` и `Check runtime and panel` на main.
Есть ручной Run workflow с `dry-run`: он показывает план без коммитов и публикации.
На роутере для этой автоматизации ничего устанавливать или запускать не нужно.

## Последовательность

1. Конвейер читает актуальный main, проверяет манифест runtime и сравнивает входы
   сборки с исходниками закреплённых бинарников: Dockerfile, исходники, профили,
   адаптеры и копируемые в SDK входы. Runtime-only материалы экспорта не заставляют
   повторно собирать ELF.
2. Если нужен новый клиент, ждёт успешных сборок MIPS, ARM64 и ARMv7 с одинаковыми
   входами. Незавершённая или неуспешная последняя попытка для того же SHA блокирует
   использование старого успешного результата. Разрешён завершившийся ancestor-build,
   если после него main получил изменения, не влияющие на бинарник.
3. Проверяет release-теги, исходники, версии, платформы, SHA-256 клиента, декодера
   и лицензий. Готовит `client-release.json`, `platform-releases.json`, клиентскую
   лицензию в `runtime-assets.json` и `web/SHA256SUMS`. MIPS-декодер остаётся
   закреплённым отдельно; сценарий не угадывает его версию.
4. Делает обычный коммит манифестов без force push. Поскольку GITHUB_TOKEN не
   запускает push-workflow после своего коммита, явно вызывает reusable-проверку
   с точным SHA и `publish-runtime: true`. Тесты и упаковка идут для этого SHA.
   Библиотеки и клиент здесь повторно не компилируются.
5. Пакетный job публикует три архива, `SHA256SUMS` и `runtime-evidence.json`.
   Последний связывает SHA runtime, номер/попытку Actions и хеши всех архивов.
   Это метаданные Release; в устанавливаемый runtime они не добавлены.
6. Перед публикацией снова проверяет main, успешные jobs тестирования и упаковки,
   evidence, все архивы и их контрольные суммы. Обновляет только `web/update.json`
   обычным коммитом `[skip ci]`. Клиент и версия панели указываются отдельно.

Обновление только панели использует закреплённые ELF. Если изменились лишь CI,
тесты, документация или сам каталог, сравнение устанавливаемого содержимого
возвращает `up-to-date`: лишнего обновления для пользователей не создаётся.
Текущий опубликованный runtime также проверяется по Release и Actions.

## Защита и разрешения

События PR, fork и чужих веток не допускаются к публикации. Код берётся с
доверенного main, а не из входящего артефакта. API сценария ограничено только
`KOPOHA-MACOHA/fptn-keenetic`. Операции с ref не используют force; изменение main
сохраняет чужой коммит и останавливает выпуск. Если main изменился во время
тестирования, устаревший пакет может остаться prerelease, но не попадёт в канал.

Публикационные jobs получают `contents: write` и `actions: read`. Сборка и тесты
сохраняют read-only доступ; запись Release разрешена отдельному пакетному job.
Используется обычный временный GITHUB_TOKEN: PAT, App key и изменения настроек
доступа не требуются. Токен API не отправляется на публичные CDN загрузки.
Теги проверяются на соответствие коммиту. Downgrade панели или клиента запрещён.

Новый оригинальный FPTN по-прежнему предлагается отдельным draft PR. Конвейер
не принимает PR, не меняет протокол и не устанавливает выпуск на роутер.
Проверки QEMU/CI не объявляются аппаратными испытаниями.

## Повторный запуск и восстановление

В summary выводятся `waiting`, `up-to-date`, `validate`, `promote`, `published`
или `stale` с причиной. `waiting` означает, что результатов ещё недостаточно;
не нужно повторно запускать дорогую компиляцию только ради публикации.
Штатное завершение следующей архитектуры продолжит работу.

Если тестирование подготовленного коммита не прошло, канал остаётся прежним.
Другие queued-события не запускают те же неуспешные тесты автоматически заново.
После устранения временной ошибки используйте Re-run failed jobs исходного
publication-run или ручной Run workflow. Манифесты не создаются повторно,
если соответствуют исходникам; ручной запуск может продолжить проверку и
упаковку такого main без компиляции зависимостей или клиента.

Ошибки доступа, сети, JSON и контрольных сумм завершаются явно. Они не считаются
отсутствием артефакта и не переключают канал на непроверенный вариант. При stale
нужно дождаться проверок актуального main. Противоречивые метаданные требуют
обычного исправления; переписывания истории и принудительного режима нет.
