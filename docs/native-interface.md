# FPTN через штатный OpkgTun0 KeeneticOS

Целевой вариант интеграции: FPTN обслуживает транспорт, KeeneticOS управляет
интерфейсом, NAT, firewall, CIDR и DNS-маршрутами. Самодельные списки/таблицы
из первоначального теста LAN в native-службе не используются.

Требуется KeeneticOS 5.x. На целевом Hopper KN-3810 проверена версия 5.1.4;
Передача из LAN через native-интерфейс проверена на устройстве: по ручным IP
получен VPN-выход. После перехода на штатный DNS перед SmartDNS и удаления
тестовых /32 пользователь также сообщил об изменении IP при доменном маршруте.

## Сборка

Артефакт Actions: **fptn-native-client**, ZIP с файлами в корне. Клиент 0.2.0.
Новый драйвер применяется после слоя Conan, версии и протокол не меняются.
Обязательны оба флага `--keenetic-connect --keenetic-native` и имя `opkgtun0`.
Без первого opt-in подключения запрещены. Старый режим fptn0 оставлен для
сравнения и отката, но новая служба использует только native-режим.

`TUNSETIFF` подключает открытый fd к существующему устройству. Проверяется
ifindex до и после операции, поддерживаются обычный TUN и MULTI_QUEUE.
Устройство не переименовывается. Клиент не вызывает TUNSETPERSIST, не назначает
адреса и не изменяет MTU/флаги интерфейса. Проверяются IPv4 10.0.0.1/32,
MTU 1420 и IFF_UP, заданные в Keenetic. Закрывается только собственный fd;
постоянный интерфейс прошивки остаётся на месте. Маршруты/DNS/firewall
RouteManager, как и в проверенном прототипе, управляются снаружи.

## Переход с работающего прототипа

Сначала скачайте готовый успешный артефакт `fptn-native-client.zip` в `/opt/tmp`.
Далее только после завершения сборки:

```sh
fptnctl stop
mkdir -p /opt/tmp/fptn-native-client
unzip -o /opt/tmp/fptn-native-client.zip -d /opt/tmp/fptn-native-client
sh /opt/tmp/fptn-native-client/fptn-native-service.sh install /opt/tmp/fptn-native-client
fptnctl setup-interface
fptnctl start
```

Установка проверяет SHA256SUMS и наличие нового флага в --help, сохраняет прежний
клиент и менеджер как `.previous`. Токен и сервер из `/opt/etc/fptn` сохраняются;
Brotli переиспользуется из установленной службы. Служба не читает старый `cidrs`.
Старый менеджер нужно остановить до замены, чтобы он удалил свои тестовые правила.
При остаточном состоянии сначала применяется recover старого менеджера.

`setup-interface` создаёт свободный OpkgTun0, описание FPTN, public, IPv4
10.0.0.1/32, MTU 1420 и adjust-mss pmtu. При существующем чужом интерфейсе
команда отказывается его менять. Для первого теста задан **no ip global**:
сценарий не добавляет default route и не переключает общий выход в интернет.
Возможность выбора такого интерфейса и необходимость дополнительных штатных
настроек NAT/global проверяются на устройстве. Если они нужны, изменяется
конфигурация Keenetic, а не добавляются обходные правила iptables в FPTN.

На странице маршрутизации Keenetic выбирается FPTN/OpkgTun0 и задаются нужные
CIDR/домены. Ожидаемое поведение нужно подтвердить запросом с телефона.
После успешной проверки конфигурация интерфейса сохраняется:

```sh
ndmc -c 'system configuration save'
```

Автозапуск пока выключен. `start/stop/status/logs/configure` сохраняются.
`stop` закрывает клиент, не удаляет интерфейс и не изменяет пользовательские
маршруты Keenetic. Включение/выключение интерфейса в UI не управляет процессом
клиента автоматически. Переход на автоматическое управление — отдельный этап.

После первого READY supervisor перезапускает завершившийся клиент с задержками
5, 10, 20, 40 и максимум 60 секунд. При каждой попытке заново определяется
основной шлюз и интерфейс выхода. После минуты жизни процесса задержка
сбрасывается; это не проверка доступности VPN. Если первое подключение не удалось,
`start` завершается ошибкой без бесконечных повторов. Повторное подключение
после падения ждёт свежего READY до 60 секунд; старый READY не переиспользуется.
`status` показывает ожидание повтора или подключение. `stop` прекращает повторы,
не меняя маршруты, DNS, интерфейс и настройки Keenetic.

Это восстановление после завершения процесса. Живой клиент с оборванным
соединением не признаётся исправным по одному READY: сетевое переподключение
остаётся обязанностью клиента и требует отдельной проверки на устройстве.

IPv6-маршрутизация пока не проверялась; driver не назначает native IPv6.
Обработка credentials и ограничения журналов те же, что у первоначальной службы.

## Откат

При неудачном native-тесте:

```sh
fptnctl stop
cp -p /opt/libexec/fptn/fptn-client-cli.previous /opt/libexec/fptn/fptn-client-cli
cp -p /opt/bin/fptnctl.previous /opt/bin/fptnctl
(cd /opt/libexec/fptn && sha256sum fptn-client-cli brotli > SHA256SUMS)
```

Созданные пользователем маршруты Keenetic перед возвратом к старому тесту
следует отключить в штатном интерфейсе. Старый `cidrs` сохранён. Команды отката
сами не удаляют OpkgTun0 или настройки Keenetic.
