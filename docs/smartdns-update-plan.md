# План апдейта SmartDNS и текущая схема DNS

Решение пользователя от 2026-10-25. Это отдельная задача по SmartDNS,
которая не должна задерживать перенос и доводку FPTN на Keenetic.

## Принято сейчас

Клиенты LAN → штатный DNS Keenetic на :53 → SmartDNS на отдельном локальном
порту 192.168.1.1:6053 (TCP и UDP).

Доменными группами, CIDR, исключениями и выбором целевого интерфейса
управляет Keenetic. FPTN предоставляет OpkgTun0/opkgtun0 и не содержит
собственных доменных списков или отдельного механизма маршрутизации.

SmartDNS сохраняет текущие upstream-серверы, доменные наборы и общие
правила обработки/подмены ответов. В этой схеме он видит запросы от роутера,
а не отдельные клиентские устройства; пользователь согласился на этот
компромисс для текущего этапа. Правила SmartDNS, завязанные на исходный IP
клиента, требуют отдельного пересмотра при переключении.

Самописный постоянный DNS-мост отменён и на роутер не устанавливался.
Его локальный черновик вынесен за пределы проекта FPTN. MagiTrickle не
устанавливается в рамках выбранной схемы.

## Переключение на штатный DNS

1. Сохранить текущие SmartDNS config/init и running-config Keenetic в
   закрытом каталоге на роутере. Не публиковать полный running-config:
   он может содержать секреты.
2. Проверить стартовый скрипт SmartDNS, занятость нового порта и текущие
   upstream-настройки Keenetic. Исключить обратное направление
   SmartDNS → штатный DNS, которое создало бы цикл.
3. Перенести только слушающий порт SmartDNS; сохранить серверы и доменные
   наборы. Проверить прямой ответ SmartDNS на новом порту.
4. Вернуть штатный DNS Keenetic на :53 и направить его upstream в SmartDNS.
   Отдельно учесть текущий filter engine opkg, получаемые от провайдера DNS,
   ручные DoH/DoT и привязки DNS к другим политикам/интерфейсам:
   добавление одного нового сервера не гарантирует, что все запросы идут в него.
5. Проверить штатное обучение домена из LAN и передачу через FPTN.
   Два временных ручных /32 для api.ipify.org удалить только после
   подтверждения доменной маршрутизации.
6. Проверить перезапуск DNS-служб; сохранять startup-config Keenetic после
   успешной проверки. При ошибке восстановить исходную схему из резервной копии.
   Не изменять общий маршрут в интернет или действующие VPN-политики.

Переключение подтверждено выводом с Hopper: ndnproxy слушает :53, SmartDNS —
192.168.1.1:6053, фактический upstream ndnproxy — только SmartDNS. Конфигурация
сохранена в startup-config. Адреса ответа появились внутри api.ipify.org со
свежим last-updated; два временных /32 удалены. После удаления пользователь
сообщил об изменении внешнего IP при обращении с телефона по доменному маршруту.
Повторное сохранение после удаления /32 было предложено; подтверждения этой
последней команды пока нет. Проверка перезагрузки DNS-служб пока не выполнена.

## Отложенный апдейт SmartDNS

Цель: SmartDNS остаётся основным DNS, сохраняет исходные IP клиентов, а
доменные маршруты по-прежнему задаются в штатной вебморде Keenetic для
любых целевых интерфейсов.

Первый вариант для оценки — генерация правил SmartDNS из групп Keenetic,
с записью адресов DNS-ответов в соответствующие штатные ipset. SmartDNS
не пересылает трафик сайтов самостоятельно: маршрутизация остаётся в ядре.
Встроенная полная синхронизация SmartDNS ↔ Keenetic не подтверждена.

Нужно решить и проверить:

- автоматическое обновление после добавления, изменения и удаления групп;
- пересекающиеся группы, приоритеты, исключения доменов и подсетей;
- несколько интерфейсов назначения без привязки к одному FPTN;
- IPv4/IPv6 и адреса, фактически выданные SmartDNS после подмены ответа;
- TTL, удаление старых адресов и сохранение ручных CIDR; текущие штатные
  hash:net-наборы нельзя считать наборами с автоматическим timeout;
- пересоздание наборов и правил прошивкой, рестарт SmartDNS и перезагрузка;
- ограничения SmartDNS 46.1 при назначении одного домена нескольким наборам;
- попадание первого соединения в нужный маршрут, расход CPU и RAM на Hopper;
- обратимая установка, отсутствие дублирующих списков для ручного обслуживания.

Если генерация правил не сохраняет штатную семантику, отдельно оценить
интеграцию с нативным обработчиком DNS-ответов. Частный протокол сокета
Keenetic требует проверки совместимости с обновлениями прошивки; решение
не должно автоматически становиться частью FPTN.

## Что уже проверено на Hopper

- SmartDNS 46.1 добавляет IP из DNS-ответа в изначально пустой временный ipset.
- Отдельный штатный ndnproxy с upstream в SmartDNS передаёт ответы в
  /var/run/fqdn-dns-mirror.sock, после чего адреса появляются внутри
  FQDN-записи api.ipify.org в domain-list9.
- Reply-only сообщение без qid принимается: оба адреса обновились с TTL 3
  и last-updated 0. Это проверка обработчика, а не готового постоянного моста.
- Туннель FPTN и передача из LAN через OpkgTun0 по IP подтверждены.

Для продолжения FPTN нужны рабочие штатные доменные маршруты, затем
проверки длительного соединения, смены rolling-туннелей, переподключения
и ресурсов. Максимальная скорость и длительная стабильность ещё не доказаны.
