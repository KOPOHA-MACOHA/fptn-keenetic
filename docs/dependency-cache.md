# Повторное использование собранных зависимостей

Первоначальный workflow экспортировал BuildKit GHA cache mode=max и снова запускал
стадию dependencies в следующем job/run. В успешном run 40173564358 этап Conan
занял около 24 минут, а повторный client-export в том же job использовал CACHED.
В run 40192823448 зависимости снова собирались. Ubuntu/SDK digests и версии
Buildx/BuildKit в этих запусках совпали. Это подтверждает проблему повторного
использования, но не доказывает конкретную причину потери записей GHA: список
Actions caches недоступен подключённому API, живые логи client выдавали 404.

## Новый механизм

`dependency-image` — отдельный OCI-образ с SDK, подготовленным upstream, `/build`
и готовыми пакетами Conan. В нём удалены только исходники/сборочные/временные
каталоги Conan; установленные пакеты сохранены и проверены check-integrity.
Образ свёрнут в один слой, чтобы удалённые деревья сборки не остались в нижних
слоях архива и не занимали кеш. Системные образы и Dockerfile frontend закреплены
на уже использованных digest, без смены версий.

Composite action `.github/actions/dependency-image`:

1. Вычисляет SHA256 только по части Dockerfile до границы dependency-image,
   sources.lock.json, профилю, prepare-source, GCC specs fix и verify-elf.
2. Восстанавливает **целый OCI-архив** через actions/cache с точным ключом.
   Не использует restore-keys от другого SDK/ABI/upstream.
3. Только при отсутствии снимка строит его; старые GHA scopes используются
   как вспомогательный источник для первоначального наполнения.
4. Проверяет структуру архива, размеры и SHA256 OCI-слоёв и выбирает linux/amd64
   manifest (это платформа компилятора, не целевого mipsel-бинарника).
5. Передаёт OCI через named build context и `DEPENDENCIES_IMAGE` прямо в FROM
   стадии client. Conan install и стадия dependencies отсутствуют в графе такой
   сборки клиента. Изменения драйвера/службы/CLI не меняют ключ снимка.
   Клиент больше не экспортирует всю среду Conan повторно в GHA layer cache,
   чтобы не дублировать крупные данные и не вытеснять подготовленный снимок.

Текущий уже запущенный workflow нельзя изменить задним числом. Исправление
публикуется с `[skip ci]`, чтобы не отменить и не перезапустить его. После его
завершения (успеха либо ошибки клиента) workflow **Prepare and verify dependency
image** подготовит снимок и на **другом runner** потребует cache-hit=true,
затем соберёт клиент из OCI. При cache miss проверочный job падает сразу,
вместо незаметной повторной компиляции зависимостей. Checkout в обоих job закреплён
на одном commit. Получается отдельный артефакт fptn-native-client-cache-verified.

Локально проверены стабильность/инвалидация ключа, целостность OCI и отклонение
опасных архивов. Docker daemon в рабочем окружении недоступен, поэтому реальная
проверка OCI FROM и повторного использования выполняется в Actions. До зелёного
verify-fresh-runner нельзя утверждать подтверждённое ускорение.

Это обычный кеш GitHub Actions: он не требует нового registry, credentials или
платных runners. Снимок всё ещё может быть удалён GitHub по сроку/квоте кеша.
В этом случае требуется его первоначальное восстановление/сборка; обещания
«никогда больше не собирать зависимости» нет. Изменение SDK, ABI, закреплённого
upstream или подготовки зависимостей создаёт новый ключ намеренно.
