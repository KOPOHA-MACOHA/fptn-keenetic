# Служба 0.14.0 и клиент 0.5.0

Транспортные сокеты HTTP/авторизации/WebSocket привязываются к реальному
исходящему интерфейсу до TCP connect. Привязка сохраняется при синхронном и
асинхронном переборе IPv4/IPv6-адресов. Ошибка привязки останавливает попытку.
Это адаптер Linux; TLS, формат пакетов и скользящие туннели остаются оригинальными.

Для native-режима больше не нужен фиктивный gateway: PPPoE/PPP с маршрутом
`default dev ppp0` допустимы. Ненужный поиск шлюза через shell не выполняется.
Сервер VPN по-прежнему может использовать IPv4; IPv6 транспортного сокета не
означает готовую маршрутизацию IPv6 устройств LAN через туннель.

Служба выбирает доступный default route основной таблицы с наименьшей метрикой,
пропускает down/linkdown, собственный OpkgTun0 и недоступные интерфейсы.
Проверяется адрес исходящего интерфейса и его индекс: DHCP renew, замена шлюза,
пересоздание PPP и смена WAN приводят к переподключению после двух устойчивых
наблюдений с интервалом около 6 секунд. Краткий скачок одного наблюдения не
перезапускает VPN. Сервер не попадает в список временно отказавших из-за смены WAN.

Если выбранного выхода нет, supervisor остаётся в состоянии «Ожидаем интернет».
После восстановления подключается сам. При явно выбранном интерфейсе не
переключается на другой. Никакие публичные адреса для определения WAN не опрашиваются;
маршруты, DNS и firewall в этом изменении не записываются.

Проверки: реальные IPv4/IPv6 TCP-сокеты с перебором недоступного и доступного endpoint;
Linux network namespaces с настоящими маршрутами, адресами и linkdown;
реальный supervisor с дочерними процессами при отсутствии сети, смене WAN и PPP.
Статический mipsel клиент собран, ABI проверен, --help/--version и probe-only
выполнены под QEMU. Зависимости восстановлены из подготовленного OCI-кэша.
Проверки ELF/QEMU и сетевые host-тесты не подтверждают работу на каждой модели
Keenetic. Аппаратные результаты указываются отдельно от результатов CI.
