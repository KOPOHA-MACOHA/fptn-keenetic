# Архив: диагностика подключения и нагрузки через CLI

Документ описывает отдельный диагностический сценарий с временным `fptn0`,
а не установку текущей native-службы. Для обычного использования см. [установку](install.md).
Для диагностики требуются клиент, Brotli и сценарий из одного совместимого артефакта.

Скачайте артефакт **fptn-connect-test**. В ZIP находится папка с тем же именем
**fptn-connect-test**. Распакуйте и загрузите эту папку целиком через SFTP
в `/opt/tmp/`. Никаких имён каталогов придумывать не надо.

Единственная команда запуска:

```sh
sh /opt/tmp/fptn-connect-test/run-connect-test.sh
```

Сценарий проверит контрольные суммы и попросит токен (ввод скрыт).
Список серверов извлекается из токена локально, через base64, Brotli и jq.
Если серверов несколько, выберите номер; Enter выбирает первый.
Если сервер один, он выбирается автоматически. Имена вводить не надо.
Токен и пароль не выводятся и не сохраняются в файлы.

Подключение делается только к выбранному серверу. Сеанс ограничен 90 секундами
после выбора; завершение timeout с кодом 124 ожидаемо. Ctrl+C завершает тест.
Как в upstream CLI, токен передаётся аргументом процесса, доступным root.

Маршруты, DNS и firewall сценарий и тестовый RouteManager не изменяют.
VPN-ядро создаёт TUN `fptn0`; Linux может добавить связанные с его адресами
подключённые маршруты. Если `fptn0` уже существует, сценарий откажется запускаться.
Этот тест ещё не направляет интернет через VPN. После проверки подключения
отдельно настраивается маршрут /32 к сервису определения внешнего IP.

## Проверка передачи данных

Для проверки передачи данных сценарий поддерживает `FPTN_DATA_TEST=1`.
Он обращается к api.ipify.org обычным путём, затем после READY повторяет HTTPS
запрос через `fptn0` к тому же IP, закреплённому через curl --resolve.
Используются отдельная таблица 30090 с маршрутом /32 и правило приоритета 50
с `iif lo`: только исходящие запросы самого роутера к проверочному IP.
Если таблица или приоритет уже заняты, тест отказывается их использовать.
Существующие маршруты, DNS и firewall не меняются.

Правило и маршрут удаляются после запроса, а также при ошибке или обычном
прерывании сценария. Успешное удаление проверяется. Принудительное SIGKILL
или отказ устройства невозможно обработать trap; после такого сбоя требуется
проверить `ip -4 rule show` и `ip -4 route show table 30090`.
Трафик теста — несколько коротких HTTPS-запросов; нагрузочный тест не проводится.


## Короткая проверка нагрузки

`FPTN_LOAD_TEST=1` включает проверку IP выше и затем скачивает 5 МиБ
с `https://speed.cloudflare.com/__down?bytes=5242880` через VPN.
Ограничения curl: 512 КиБ/с, 15 секунд, тело в `/dev/null`.
IP Cloudflare получается коротким запросом до подключения и закрепляется
через `--resolve`; для него временно создаются такие же локальные /32 и правило.
После скачивания они удаляются. DNS и маршруты устройств LAN не изменяются.

Раз в секунду измеряются общий CPU по `/proc/stat`, RSS ELF-процесса клиента
и MemAvailable. CPU указан относительно всех логических процессоров вместе;
он включает прочую работу роутера. Если PID клиента не найден, нагрузочная проверка прекращается.
Скачивание прерывается при MemAvailable ниже 16 МиБ или CPU от 90% три замера
подряд. Эти ограничения не гарантируют защиту от зависания устройства.
Небольшой тест с ограничением скорости не измеряет максимальную пропускную
способность и не проверяет длительную стабильность.

Пример запуска с обфускацией и двойным туннелем:

```sh
FPTN_LOAD_TEST=1 FPTN_BYPASS_METHOD=obfuscation \
FPTN_CONNECTION_STRATEGY=dual-rolling-tunnel \
sh /opt/tmp/fptn-connect-test/run-connect-test.sh
```


### Отдельный CPU клиента

Сценарий ожидает READY второго туннеля в dual-rolling-tunnel, затем собирает
5 отсчётов простоя до загрузки, отсчёты во время скачивания и 5 после.
Каждый интервал — примерно секунда. Печатаются посекундные строки `[CPU]`
и взвешенные по процессорным тикам средние/пики `[ИТОГ]` для каждой фазы.
CPU процесса берётся из utime+stime `/proc/PID/stat` (все его потоки).
CPU FPTN и общий CPU используют одну шкалу: 100% — все логические процессоры
вместе. На четырёх логических процессорах занятый целиком один соответствует
примерно 25%. Время ядра вне процесса (например, softirq) входит в общий CPU,
но не обязательно в CPU FPTN. Отдельный всплеск меньше секунды этим способом
не локализуется: видна его доля в целом интервале.

Это простой подключённого туннеля, не роутера без FPTN. Фоновая работа других
служб и трафик LAN продолжаются. PID определяется через `/proc/PID/exe`;
проверяется время старта процесса, чтобы не принять повторно использованный PID.
