# FPTN для Keenetic / Entware

Экспериментальный перенос [FPTN](https://github.com/fptn-project/fptn).
Первая цель — **Hopper KN-3810 EAEU**, EN7528DU / MIPS 1004Kc,
MIPS32r2 little-endian, o32, soft-float; KeeneticOS Linux 4.9.

**Статус: подключение и передача данных проверены на Hopper KN-3810;
LAN-передача по CIDR через штатный OpkgTun0 KeeneticOS также подтверждена.
Штатный DNS перед SmartDNS настроен; служба и панель поддерживают установку, обновление и восстановление подключения.**
Этот репозиторий не является официальным выпуском FPTN или Keenetic.

## Установка и управление

Панель **0.15.0**: **http://192.168.1.1:1111/**.
[Установка с нуля, обновление и удаление](docs/install.md),
[архитектуры и уровень проверки](docs/platforms.md).
Готовый полный архив: `fptn-keenetic-mipsel-mips32r2-softfloat.tar.gz` в выпусках
`runtime-COMMIT`. Дополнительно опубликованы экспериментальные
`fptn-keenetic-aarch64.tar.gz` и `fptn-keenetic-armv7-softfloat.tar.gz`.
Клиент **0.5.0** основан на оригинальном FPTN **0.4.6**;
версия и точная сборка показаны в панели. На роутере ничего не компилируется.

Токен, сервер и вход задаются в браузере. Можно создать отдельный логин/пароль
либо использовать root Entware. Существующие PHP/lighttpd переиспользуются;
bootstrap ставит недостающие пакеты. Маршруты по доменам/CIDR, DNS и firewall
настраиваются в Keenetic, а FPTN использует штатный **OpkgTun0**.
Экспериментальный IPv6 включается отдельно: добавляются адрес собственного
интерфейса и ограниченное им правило NAT66; маршруты остаются в Keenetic.
Автозапуск включается отдельно после проверки подключения.

```sh
fptnctl status          # состояние и фактически выбранный сервер
fptnctl start           # подключение с сохранёнными параметрами
fptnctl stop            # остановка без удаления интерфейса/маршрутов
fptnctl enable          # автозапуск после загрузки Entware
fptnctl disable         # выключить автозапуск, оставить текущее соединение
fptnctl web-reset-login # снова открыть создание учётной записи
fptnctl uninstall       # удалить программу, оставить конфигурацию и маршруты
```

[Функции панели](docs/web-ui.md), [смена WAN/PPPoE](docs/release-0.14.md), [экспериментальный IPv6](docs/release-0.15.md),
[совместимость с оригиналом и оставшиеся задачи](docs/feature-parity.md),
[получение изменений upstream](docs/upstream-updates.md).
Подключение и штатная маршрутизация клиента 0.4.0 проверены на Hopper.
Новый клиент 0.5.0, смена WAN и IPv6 проверяются автоматически; аппаратная
проверка новых возможностей добровольная и не заявляется выполненной. Новый путь чистой
установки проверяется в Actions и ещё требует испытания на чистом устройстве.

## Почему статическая сборка

На проверяемом устройстве Entware 2025.05: glibc 2.27, GCC runtime 8.4,
около 68 МиБ доступной памяти, без swap; `/dev/net/tun` присутствует.
FPTN требует C++20. Прототип использует новый компилятор из OpenWrt SDK,
но **не устанавливает пакеты OpenWrt**: выдаёт отдельные статические ELF с musl.
Они не заменяют `/opt/lib` и не используют системную `libstdc++`.
Базовая совместимость подтверждена на реальном Hopper KN-3810 EAEU:
2026-10-24 пользователь запустил probe из выпуска `probe-4ed5766` и получил
`probe: PASS`. Прошли потоки, atomic64, исключения и корутины C++20.
Работа VPN, TLS, DNS, маршрутизация и нагрузка этим тестом не проверялись.

## Что собирается

В [Actions](../../actions) запускается workflow `Build prototype`:

1. `probe` — небольшой статический C++20 бинарник: потоки, атомики,
   исключения, корутины. Проверяется ABI ELF и запуск под QEMU.
2. `client` — FPTN CLI с тем же SDK; проверяется ELF и `--help` под QEMU.

Артефакты: `keenetic-mipsel-probe` и `fptn-native-client`.
Архивы содержат SHA256 и сведения об исходниках.
В опубликованном прототипе 0.0.0 подключение безусловно заблокировано.
Клиент 0.1.0 разрешает только явный запуск с `--keenetic-connect`:
маршрутизация, DNS и firewall управляются снаружи и не изменяются RouteManager.
2026-10-25 на Hopper подтверждены obfuscation, два rolling-туннеля и HTTPS через
fptn0 с изменением внешнего IPv4. Загрузка 5 МиБ с ограничением около 4,2 Мбит/с
прошла; CPU клиента в среднем 7,8% всех логических процессоров, RSS до 18,3 МиБ.
Это короткий тест, не проверка предельной скорости или длительной стабильности.
Подробности и ограничения: [тест подключения](docs/tunnel-test.md).
Прототип 0.2.0: [штатный OpkgTun0 и native-служба](docs/native-interface.md).
FPTN подключается к постоянному интерфейсу прошивки; CIDR и домены задаются
на штатной странице маршрутизации Keenetic. В native-службе нет собственных таблиц маршрутизации и DNS-списков;
необязательный NAT66 ограничен только своим интерфейсом. Проверены локальные тесты драйвера
и жизненного цикла службы. Сборка MIPS завершилась успешно; native-передача
на Hopper подтверждена маршрутом по IP из LAN. Автозапуск выключен.

Принятое решение по DNS и отложенные задачи SmartDNS записаны отдельно:
[план апдейта SmartDNS](docs/smartdns-update-plan.md). Доработка DNS-интеграции
не блокирует разработку FPTN; самописный постоянный мост не установлен.

[Первоначальная ручная служба](docs/manual-service.md) оставлена для истории и
отката. Её собственная CIDR-маршрутизация не развивается: маршруты принадлежат Keenetic.

Не запускайте сторонний исходный CLI с токеном: в нём есть изменение default
route, firewall и DNS, не адаптированное к Keenetic. Существование TUN ещё
не доказывает совместимость маршрутизации или приемлемую скорость.

## Первый тест с телефона

Вставьте блок в Termius. Он скачивает только диагностический бинарник
из [предварительного выпуска](https://github.com/KOPOHA-MACOHA/fptn-keenetic/releases/tag/probe-4ed5766), проверяет SHA256 и запускает его:

```sh
(
set -eu
mkdir -p /opt/tmp
FPTN_TEST_DIR=$(mktemp -d /opt/tmp/fptn-probe.XXXXXX)
cd "$FPTN_TEST_DIR"
FPTN_URL="https://github.com/KOPOHA-MACOHA/fptn-keenetic/releases/download/probe-4ed5766/fptn-platform-probe"
if command -v curl >/dev/null 2>&1; then
  curl -fL --connect-timeout 15 --max-time 120 "$FPTN_URL" -o fptn-platform-probe
else
  wget -T 60 -O fptn-platform-probe "$FPTN_URL"
fi
echo "832674ff7859ddca7832971ac0acb41e711a173b4e88d84742333eb346c4dec2  fptn-platform-probe" | sha256sum -c -
chmod 700 fptn-platform-probe
./fptn-platform-probe
)
```

Программа не открывает TUN, не подключается к серверу и не меняет настройки.
Ожидается `probe: PASS`. Она подтверждает только базовую совместимость ABI,
а не скорость, стабильность VPN, TLS или работу сетевого стека.

## Сборка на компьютере

Требуется Docker BuildKit на Linux x86_64:

```sh
docker build --target probe-export --output type=local,dest=out/probe .
docker build --target client-export --output type=local,dest=out/client .
```

При работе через корпоративный HTTPS proxy можно передать CA:
`--secret id=proxy_ca,src=/path/to/combined-ca-bundle.pem`.
Сертификат используется только в шагах сборки и не включается в артефакты.

## Обновления и поддержка

`sources.lock.json` фиксирует FPTN и четыре зависимости, которые оригинал
скачивает с плавающих веток. `scripts/prepare-source.py` применяет небольшие
проверяемые преобразования и завершается ошибкой при изменении ожидаемой структуры.
Оригинальные исходники не копируются в этот репозиторий.

Новые стабильные выпуски оригинального FPTN проверяются ежедневно через Actions.
Для новой версии автоматически создаётся отдельный draft PR с обновлённым SHA,
сборкой клиента и тестами панели. Подробнее: [обновления оригинала](docs/upstream-updates.md).
Автоматического merge и установки нового upstream на роутер нет: после проверок
нужно проверить клиент на устройстве и отдельно опубликовать выпуск. SDK tag и полный транзитивный граф Conan пока не
зафиксированы digest/lockfile: это воспроизводимая процедура, но ещё не гарантия
побитово одинакового результата. Их фиксация — следующий этап после первой сборки.
